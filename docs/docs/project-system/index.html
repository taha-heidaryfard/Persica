Project Architecture & .persi_env

New in v0.13.0

Structure multi-file Persica projects, manage modules, configure persica.toml, and use isolated local package environments.

Overview & Philosophy

Introduced in v0.13.0, Persica features a built-in, zero-dependency project system. It enables developers to structure large-scale codebases cleanly with modular imports, project-level unit testing, and isolated package environments.

Scaffolding a New Project

To create a new Persica project with complete scaffolding in one command, run:

Terminal
persica new analytics_app
cd analytics_app
Output:
Created new Persica project 'analytics_app'
  - Created persica.toml
  - Created src/main.persi
  - Created .persi_env/ environment directory

Generated Project Layout:

📁 analytics_app/
├── 📄 persica.toml                         // Project manifest configuration
├── 📁 src/                                    // Application source code
└── 📄 main.persi                           // Main application entrypoint
└── 📁 .persi_env/                             // Isolated local dependencies folder

The `persica.toml` Manifest

The persica.toml file is the root configuration of your package. It uses a clean, zero-dependency TOML structure:

persica.toml
[package]
name = "analytics_app"
version = "0.1.0"
entry = "src/main.persi"
source = "src"

[environment]
env_dir = ".persi_env"
FieldDefaultDescription
package.name""Unique identifier for the project.
package.version"0.1.0"Semantic version number of the package.
package.entry"src/main.persi"File executed when running persica run or persica persica.toml.
package.source"src"Root directory for internal module resolution.
environment.env_dir".persi_env"Dedicated folder for isolated local modules and external packages.

The Isolated `.persi_env` Environment

In modern programming, isolating project dependencies is critical. In Python, this is done via virtual environments (.venv), but virtualenvs duplicate Python executable binaries and dynamic link libraries.

Persica’s Clean Design:

Persica’s .persi_env is completely configuration-driven. Zero executable binaries are duplicated. The compiler automatically links your local environment into the module resolution path.

Module Resolution Hierarchy

When you write an import statement such as from my_library import calculate;, the compiler searches through four tiered layers in strict order:

  1. Current File Directory: Relative to the invoking script (./my_library.persi or ./my_library/mod.persi).
  2. Project Source Directory: Configured as source in persica.toml (e.g. src/my_library.persi).
  3. Local Environment (.persi_env): Configured as env_dir (e.g. .persi_env/my_library/mod.persi).
  4. Built-in Standard Library: The self-hosted stdlib (std.math, std.collections, etc.).

CLI Project Commands

Running the Project:

Terminal
persica run
Output:
Running project 'analytics_app' (v0.1.0)...
[Application output]

Running Automated Project Tests:

Discovers and executes every *.persi test file in the tests/ directory:

Terminal
persica test
Output:
Running 3 test file(s) in 'tests' directory:
  - tests/math_test.persi ... PASSED
  - tests/model_test.persi ... PASSED
  - tests/api_test.persi ... PASSED

Summary: 3 passed, 0 failed

Direct Manifest Invocation:

You can explicitly point Persica to a configuration and optionally specify an alternate script to run within that project context:

Terminal
# Run the entry file defined in persica.toml
persica persica.toml

# Run an alternate script with the project paths loaded
persica persica.toml src/benchmarks/perf.persi
