# قانون مستندسازی آپدیت‌ها

هر قابلیت یا نسخه باید هم‌زمان با کد مستند شود. تغییر بدون documentation کامل‌شده تلقی نمی‌شود.

## برای هر قابلیت

فایل موضوعی مربوط در `docs/learn/language/` یا `docs/project/compiler/` باید شامل این بخش‌ها باشد:

- هدف قابلیت
- syntax یا API
- semantics دقیق
- حداقل یک مثال صحیح
- خطاها و edge caseها
- محدودیت‌های فعلی
- اثر بر compatibility

اگر قابلیت موضوع جدیدی است، فایل جدا ساخته و در `docs/README.md` لینک می‌شود.

## برای هر نسخه

یک فایل مستقل در `docs/project/releases/vX.Y.Z.md` براساس `TEMPLATE.md` لازم است. این فایل باید موارد زیر را ثبت کند:

- خلاصه و هدف نسخه
- قابلیت‌های اضافه‌شده
- تغییرات compiler/runtime/tooling
- breaking changeها
- bug fixها
- migration
- تست و معیار پذیرش
- محدودیت‌ها و کارهای بعدی

## فایل‌های همراه

- `CHANGELOG.md`: فهرست کوتاه و قابل اسکن
- `ROADMAP.md`: فقط آینده، نه شرح کامل نسخه‌ی منتشرشده
- `README.md`: قابلیت‌های اصلی و راه شروع
- topic docs: منبع حقیقت رفتار فعلی
- release docs: رفتار و تصمیم‌های همان نسخه

## تغییر bug fix

حتی bug fix کوچک باید:

1. regression test داشته باشد.
2. در release note نسخه‌ی بعدی ثبت شود.
3. اگر رفتار documented تغییر کرده، topic doc را اصلاح کند.

## بررسی لینک و مثال

پیش از release باید تمام لینک‌های نسبی resolve شوند و مثال‌های قابل اجرا با binary همان نسخه check شوند.
